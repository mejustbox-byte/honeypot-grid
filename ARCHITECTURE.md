# Архитектура Honeypot Grid

## Статус и принципы

Это спецификация будущей реализации. Доверительные границы важнее выбора облака или runtime. Control plane отделён от недоверенных приманок и файлов; при отказе политика запрещает новые действия. Dry-run является режимом по умолчанию.

## Менеджер

Менеджер хранит желаемое состояние и сопоставляет его с runtime. План содержит ID лаборатории, допустимые сервисы и образы по digest, сетевую политику, ресурсы, TTL, владельца и ссылку на разрешение. Он не принимает команды оболочки из телеметрии или ответов ИИ.

Жизненный цикл: draft → validated → awaiting approval → provisioned → observing → quarantined → destroyed. Ошибки валидации не приводят к provisioning. Human-in-the-loop связывает подтверждение с хешем полного плана, идентичностью оператора и сроком действия; подтверждение одноразовое. Изменение scope, образа или сетевой политики требует нового плана.

Reconciliation должен быть идемпотентным. Истечение TTL останавливает приманку и запускает cleanup ресурсов. Emergency stop сначала блокирует сетевой доступ и новые задания, затем останавливает runtime. Аудит фиксирует переходы состояния и решения политики, но не сырые payload или секреты.

## Контейнеризация и runtime

| Уровень | Требование |
| --- | --- |
| Хост | Выделенная лабораторная VM, без production credentials и соседних рабочих нагрузок |
| Контейнер | Непривилегированный UID, drop capabilities, no-new-privileges, read-only rootfs |
| Файловая система | Ограниченный tmpfs; без hostPath, сокета runtime и домашних каталогов хоста |
| Ядро | Seccomp и доступный механизм MAC; лимиты CPU, памяти, процессов, диска |
| Образы | Фиксация digest, проверка происхождения, зависимостей и лицензии |
| Сервис | Синтетические данные; нет рабочей аутентификации production |

Запрещены privileged, host network/PID/IPC и доступ к Docker socket. Rootless runtime полезен, но не заменяет VM-изоляцию и сетевой enforcement. Компрометация контейнера считается ожидаемым сценарием.

## Сетевая изоляция, egress deny и pivoting

Менеджер и административный API находятся в отдельном control plane. Каждая приманка получает отдельный namespace/сегмент. Ingress допускается только для утверждённого лабораторного сценария и конкретных портов. Ни менеджер, ни административные интерфейсы не публикуются вместе с приманкой.

Default deny применяется к новым исходящим соединениям, IPv4 и IPv6. Блокируются DNS, cloud metadata, link-local, loopback хоста, production, соседние приманки и любые произвольные внешние назначения. Фильтрация выполняется вне приманки: host firewall плюс сетевые правила облака. Одна лишь настройка приложения недостаточна.

Разрешённые ответы на входящий сервисный трафик ограничиваются состоянием соединения и лимитами; они не дают права открывать новые исходящие соединения. Сервис не предоставляет proxy, forwarding, произвольный fetch или shell. HTTP redirects не меняют scope.

Предпочтительный сбор событий — ограниченный канал stdout/локального runtime, читаемый агентом хоста. Приманке не нужны сетевой доступ к сборщику или его credentials. Если позднее потребуется сетевой транспорт, это отдельное документированное исключение к deny: только выделенный endpoint, фиксированный порт, узкая идентичность, квота и проверка схемы. Такой канал не должен маршрутизировать произвольный трафик.

## Сбор и обезличивание телеметрии

Поток: приманка → агент → валидация схемы → приватное хранилище → privacy pipeline → review → публичный экспорт. Агент имеет write-only доступ к ingest, но не к управлению приманками. Очередь ограничена; переполнение фиксируется агрегированной метрикой, без снятия ограничений.

Минимальный нормализованный event: версия схемы, случайный event ID, псевдоним sensor ID, время, тип сервиса, категория события и уровень достоверности. Ограничиваются размер сообщения, глубина JSON, число полей и частота. Неизвестные поля отклоняются; строки экранируются для отчётов.

По умолчанию не собираются пароли, токены, полные тела запросов и содержимое файлов. Сырые адреса, имена пользователей, пути, query strings, заголовки и stack traces могут содержать чувствительные данные. Они удаляются или заменяются до экспорта. Для временной корреляции допускается keyed HMAC с ключом вне репозитория и периодической ротацией. Обычный хеш адреса не защищает от перебора.

Псевдонимизация не равна анонимизации. Публичный профиль использует только allowlist полей, укрупнённое время, агрегированные счётчики и подавление редких групп по утверждённому порогу. Даже после этого требуется проверка риска повторной идентификации человеком. Сроки хранения raw, normalized и export задаются отдельно; истечение удаляет также связанные копии по установленной политике.

## Sandbox анализа файлов

Загрузка помещается в закрытый карантин с лимитами размера и количества, без публичного URL. Файл никогда не исполняется сборщиком или менеджером. Первым этапом служит статический анализ в отдельной одноразовой VM/microVM без сети, metadata, общих дисков и cloud credentials.

Архивы ограничены по глубине, количеству объектов и суммарному распакованному размеру; пути нормализуются, symlink и path traversal отклоняются. Парсеры также недоверенны: им нужны таймауты и ограничения ресурсов. Динамический анализ не входит в первый MVP и требует отдельного containment review.

Результат возвращается через ограниченный структурированный канал, проходит валидацию и privacy review. VM уничтожается после задания независимо от успеха. Исходные образцы не попадают в git, CI, issue attachments или внешние репутационные сервисы.

## IoC и ИИ

Внутренний IoC содержит тип, значение, источник/event reference, метод извлечения, first/last seen, confidence, основание и срок пересмотра. Наблюдение не доказывает вредоносность; адрес может принадлежать посреднику или общему сервису.

Публичный экспорт отделён от внутреннего набора. Адреса инфраструктуры и персональные данные исключаются. Домены, URL и хеши файлов тоже требуют проверки на чувствительность; секреты в URL не допускаются. Публикация, включая будущие STIX-профили, требует human review. В тестах используются только синтетические IoC.

Будущий ИИ получает очищенный текст как данные, без tools для исполнения. Требуются ссылки на доказательства, confidence и обозначение неопределённости. Prompt injection из событий не может менять scope, policy, доступы или экспорт.

## Наблюдаемость

Метрики: доля потерь событий, ошибки схемы, нарушение политики, время уничтожения runtime, заполнение очереди и задержка очистки. Аудит размещается отдельно от приманок с ограничением записи и доступа. При недоступности enforcement, audit или privacy pipeline новые развёртывания и экспорты блокируются.
