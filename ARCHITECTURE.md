# Архитектура Honeypot Grid

## Статус и принципы

Реализованы policy/manager, private storage, telemetry, review/intelligence, quarantine/static worker, bounded sensors и opt-in Docker adapter. По умолчанию используется mock; Docker profile не имеет внешнего ingress. Добавлены opt-in QEMU executor и bounded stdout/Docker-log transport; реальный VM/Docker acceptance, cloud provisioning и внешняя auth остаются открытыми. Доверительные границы важнее числа функций; подробное состояние — [RUNBOOK.md](RUNBOOK.md).

## Менеджер

Менеджер хранит желаемое состояние и сопоставляет его с runtime. План содержит ID лаборатории, допустимые сервисы и образы по digest, сетевую политику, ресурсы, TTL, владельца и ссылку на разрешение. Он не принимает команды оболочки из телеметрии или ответов ИИ.

Текущий жизненный цикл: validation до записи → awaiting-approval → observing → destroyed для mock. Docker добавляет durable provisioning до внешнего create и quarantined при ошибке; reconcile очищает незавершённые ресурсы. Ошибки валидации не приводят к provisioning. Human-in-the-loop связывает подтверждение с хешем полного плана, идентичностью оператора и сроком действия; подтверждение одноразовое. Изменение scope, образа или сетевой политики требует нового плана.

Reconciliation должен быть идемпотентным. Истечение TTL запрещает apply; expire/reconcile запускают cleanup. Для гарантированной остановки требуется независимый supervisor. Текущий stop удаляет принадлежащий плану контейнер и проверяет отсутствие; network-none не открывает ingress. Целевой emergency stop будущей ingress topology также должен блокировать трафик вне runtime. Аудит фиксирует переходы состояния и решения политики, но не сырые payload или секреты.

## Контейнеризация и runtime

| Уровень | Требование |
| --- | --- |
| Хост | Выделенная лабораторная VM, без production credentials и соседних рабочих нагрузок |
| Контейнер | Непривилегированный UID, drop capabilities, no-new-privileges, read-only rootfs |
| Файловая система | Ограниченный tmpfs; без hostPath, сокета runtime и домашних каталогов хоста |
| Ядро | Seccomp и доступный механизм MAC; лимиты CPU, памяти, процессов, диска |
| Образы | Фиксация digest, проверка происхождения, зависимостей и лицензии |
| Сервис | Синтетические данные; нет рабочей аутентификации production |

Внутри приманки запрещены privileged, host network/PID/IPC и Docker socket. Доверенный manager использует фиксированный socket только на утверждённом lab host. Rootless runtime полезен, но не заменяет VM-изоляцию и сетевой enforcement. Компрометация контейнера считается ожидаемым сценарием.

## Сетевая изоляция, egress deny и pivoting

Менеджер и административный API находятся в отдельном control plane. Каждая приманка получает отдельный namespace/сегмент. Ingress допускается только для утверждённого лабораторного сценария и конкретных портов. Ни менеджер, ни административные интерфейсы не публикуются вместе с приманкой.

Default deny применяется к новым исходящим соединениям, IPv4 и IPv6. Блокируются DNS, cloud metadata, link-local, loopback хоста, production, соседние приманки и любые произвольные внешние назначения. Фильтрация выполняется вне приманки: host firewall плюс сетевые правила облака. Одна лишь настройка приложения недостаточна.

Разрешённые ответы на входящий сервисный трафик ограничиваются состоянием соединения и лимитами; они не дают права открывать новые исходящие соединения. Сервис не предоставляет proxy, forwarding, произвольный fetch или shell. HTTP redirects не меняют scope.

Предпочтительный сбор событий — ограниченный канал stdout/локального runtime, читаемый агентом хоста. Приманке не нужны сетевой доступ к сборщику или его credentials. Если позднее потребуется сетевой транспорт, это отдельное документированное исключение к deny: только выделенный endpoint, фиксированный порт, узкая идентичность, квота и проверка схемы. Такой канал не должен маршрутизировать произвольный трафик.

## Сбор и обезличивание телеметрии

Поток: приманка → агент → валидация схемы → приватное хранилище → privacy pipeline → review → публичный экспорт. Целевой отдельный агент должен иметь write-only доступ к ingest. Текущий доверенный локальный Docker collector имеет доступ к runtime socket и не является write-only изолированным агентом. Очередь ограничена; переполнение фиксируется агрегированной метрикой, без снятия ограничений.

Текущий ingest event: schema_version, event_id, sensor_id, source_ip, timestamp, service, category. Идентификаторы/IP не сохраняются напрямую: ingestion заменяет их HMAC. Отдельный transport envelope содержит transport_version=1, random delivery_id и пяти-полевый sensor event. Sensor stdout не включает IP; collector хранит HMAC source-uncollected, не выдумывая source_ip для legacy import. Receipt и event записываются атомарно; повтор после рестарта/rotation не дублирует событие, изменение содержимого под тем же ID отклоняется. Dedup receipt удаляется вместе с retention. Блокировка/ошибка после committed batch допускает повтор всего snapshot. Docker logs читаются между двумя проверками ownership/security. Ограничиваются размер сообщения, глубина JSON, число полей и частота. Неизвестные поля отклоняются; строки экранируются для отчётов.

По умолчанию не собираются пароли, токены, полные тела запросов и содержимое файлов. Сырые адреса, имена пользователей, пути, query strings, заголовки и stack traces могут содержать чувствительные данные. Они удаляются или заменяются до экспорта. Для временной корреляции допускается keyed HMAC с ключом вне репозитория и периодической ротацией. Обычный хеш адреса не защищает от перебора.

Псевдонимизация не равна анонимизации. Публичный профиль использует только allowlist полей, укрупнённое время, агрегированные счётчики и подавление редких групп по утверждённому порогу. Даже после этого требуется проверка риска повторной идентификации человеком. Сроки хранения raw, normalized и export задаются отдельно; истечение удаляет также связанные копии по установленной политике.

## Sandbox анализа файлов

Загрузка помещается в закрытый карантин с лимитами размера и количества, без публичного URL. Файл никогда не исполняется сборщиком или менеджером. Первым этапом служит статический анализ в отдельной одноразовой VM/microVM без сети, metadata, общих дисков и cloud credentials.

Архивы ограничены по глубине, количеству объектов и суммарному распакованному размеру; пути нормализуются, symlink и path traversal отклоняются. Парсеры также недоверенны: им нужны таймауты и ограничения ресурсов. Динамический анализ не входит в первый MVP и требует отдельного containment review.

Результат возвращается через ограниченный структурированный канал, проходит валидацию и privacy review. VM executor запускает фиксированный QEMU TCG argv: 256 MiB, 1 vCPU, без NIC/monitor/host mounts, raw read-only input disk, sealed memfd kernel/initramfs/sample и 30-секундный deadline. Одноразовый approval связывает sample, trusted boot hashes, scope и policy. Вывод ограничен 64 KiB и проверяется по nonce/hash/schema. Process-group cleanup и parent-death signal уничтожают процесс; guest poweroff завершает успешный boot. Нет постоянного writable guest disk. Реальная boot/teardown проверка остаётся отдельным gate. Исходные образцы не попадают в git, CI, issue attachments или внешние репутационные сервисы.

## IoC и ИИ

Внутренний IoC содержит тип, значение, источник/event reference, метод извлечения, first/last seen, confidence, основание и срок пересмотра. Наблюдение не доказывает вредоносность; адрес может принадлежать посреднику или общему сервису.

Публичный экспорт отделён от внутреннего набора. Адреса инфраструктуры и персональные данные исключаются. Домены, URL и хеши файлов тоже требуют проверки на чувствительность; секреты в URL не допускаются. Публикация, включая будущие STIX-профили, требует human review. В тестах используются только синтетические IoC.

Текущий offline анализ получает только очищенные группы. Validator структурированного model proposal проверяет hash отчёта, индексы evidence и допустимые сигналы; подключённого LLM provider нет. Будущий ИИ получает данные без tools для исполнения. Требуются ссылки на доказательства, confidence и обозначение неопределённости. Prompt injection из событий не может менять scope, policy, доступы или экспорт.

## Наблюдаемость

Метрики: доля потерь событий, ошибки схемы, нарушение политики, время уничтожения runtime, заполнение очереди и задержка очистки. Аудит размещается отдельно от приманок с ограничением записи и доступа. При недоступности enforcement, audit или privacy pipeline новые развёртывания и экспорты блокируются.

## Транзакции и ограничения

Полный план хеширует конфигурацию, обязательные декларации изоляции, выбранный adapter и время жизни. SQLite хранит план, approval и состояния awaiting-approval → observing → destroyed. Draft/validation представлены проверкой до записи. TTL проверяется перед apply, а перевод состояния в destroyed запускается командой expire. Docker adapter добавляет durable provisioning/quarantined и проверяемый stop; детали в [RUNBOOK.md](RUNBOOK.md).

Approval проверяет заявленного owner и срок, потребляется атомарно. Идентичность доверена локальной ОС, --operator не доказывает личность. Изменение доверенного scope проверяется перед apply обоих адаптеров. Docker проверяет cgroup/MAC/seccomp, image и ownership/security state; attestation не доказывает инфраструктурную изоляцию. Для внешнего control plane требуется отдельная auth. Аудит не включает входные payload, но локальная база изменяема её владельцем.
